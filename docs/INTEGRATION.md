# Как раздать команде и подключить к рабочему проекту

Инструмент задуман так, что **токен Figma нужен одному человеку**, а пользуются все.
Выгруженный макет — это обычные файлы в репозитории проекта.

## Схема

```
один разработчик:   figma-vault add <ссылка>  →  .figma-vault/  →  git commit
все остальные:      git pull                  →  агент читает через MCP
```

Токен участвует только в первом шаге. У остальных его нет и не требуется:
лимиты Figma их не касаются, доступ к файлу в Figma — тоже.

---

## 1. Как раздать другим разработчикам

Пакет ставится в проект тремя способами. Работа с ним дальше одинаковая.

### Вариант А — из git-репозитория (не нужен доступ к npm-регистри)

```bash
npm i -D github:<организация>/figma-vault
```

Сборка выполняется автоматически при установке (`prepare`-скрипт), TypeScript
у потребителя не требуется. Подходит, когда на работе нельзя публиковать в npm,
но есть внутренний GitHub/GitLab. Для GitLab — `npm i -D git+ssh://git@gitlab.example.com/team/figma-vault.git`.

### Вариант Б — внутренний npm-регистри

```bash
npm publish --registry https://npm.internal.example.com
npm i -D @<организация>/figma-vault
```

Перед публикацией поменяйте `name` в `package.json` на scoped-имя организации.

### Вариант В — публичный npm

```bash
npm publish
npx figma-vault init
```

Имя `figma-vault` может быть занято — проверьте `npm view figma-vault` и при
необходимости смените на scoped.

---

## 2. Подключение к рабочему проекту

В корне проекта, куда верстается интерфейс:

```bash
npx figma-vault init
```

Команда делает четыре вещи и **не трогает то, что уже настроено**:

| что | результат |
|---|---|
| `.figma-vault/` | каталог хранилища |
| `.mcp.json` | добавляется сервер `figma-vault`, чужие записи сохраняются |
| `.gitignore` | дописывается `.env`, если его там нет |
| `.claude/commands/figma.md` | слэш-команда `/figma` для Claude Code |

Запись в `.mcp.json` использует `npx`, а не абсолютный путь — конфиг переносим
между машинами и операционными системами.

Дальше:

```bash
echo "FIGMA_TOKEN=figd_..." > .env      # только у того, кто выгружает
npx figma-vault add "<ссылка на фрейм>"
git add .figma-vault && git commit -m "макет: экран входа"
```

## 3. Одна команда со ссылкой

После `init` в Claude Code доступна слэш-команда:

```
/figma https://www.figma.com/design/КЛЮЧ/Проект?node-id=127-4532
```

Она выгружает макет, читает его через MCP и верстает, следуя конвенциям проекта.
В саму команду зашиты особенности формата: сортировка секций по `layout.y`,
auto-layout как flex, где искать ассеты, что делать при пустых `tokens`.

Для Codex и других агентов слэш-команды нет, но сервер тот же — он берётся
из `.mcp.json`. Достаточно попросить: «выгрузи макет <ссылка> через figma-vault
и свёрстай по нему», агент вызовет CLI и MCP сам.

## 4. Дом и работа

Дома и на работе это один и тот же пакет, различаются только два момента.

**Токен.** Personal access token привязан к аккаунту Figma. Для рабочих макетов
нужен токен рабочего аккаунта, у которого есть доступ к файлу. Держите их в разных
`.env` — файл лежит в проекте и в git не попадает.

**Что коммитить.** Рекомендуется коммитить `.figma-vault/` целиком: это и есть
способ раздать макеты команде. Размер на реальном макете — около 300 КБ на `doc.json`
плюс ассеты. Если политика компании запрещает держать дизайн-артефакты в репозитории
кода, добавьте `.figma-vault/` в `.gitignore` — тогда каждому разработчику понадобится
свой токен, и выгружать макет будет каждый сам.

`raw.json` — это сырой ответ Figma, он нужен только для отладки нормализатора.
Если размер репозитория критичен, добавьте `.figma-vault/**/raw.json` в `.gitignore`:
MCP-сервер к нему не обращается.

## 5. Проверка на машине, где токена нет

Токен нужен только для выгрузки новых макетов. Всё остальное — чтение макетов
агентом — работает без него, и это штатный режим для всей команды кроме одного человека.

Поэтому проверить установку на рабочей машине можно полностью, не создавая токен:

```bash
npx figma-vault init
npx figma-vault demo     # демо-макет едет внутри пакета
npx figma-vault check
```

`check` поднимает настоящий MCP-сервер дочерним процессом, здоровается с ним
по протоколу и выводит отчёт:

```
[ OK ] .mcp.json — сервер figma-vault зарегистрирован
[ OK ] Хранилище — .figma-vault/, макетов: 1
[ OK ] Макет EXAMPLE1234_1_1 — узлов: 29
[ OK ] MCP-сервер — инструментов: 6 (vault_list, vault_get_doc, …)
[ВНИМ] FIGMA_TOKEN — не задан — читать макеты из хранилища можно, выгружать новые нельзя
```

Отсутствие токена помечается как ВНИМ, а не СБОЙ: это не поломка, а обычное
состояние рабочего места. Код возврата при реальных проблемах — 1, так что команду
можно ставить в CI.

Дальше попросите агента: «свёрстай макет EXAMPLE1234_1_1 из figma-vault». Он прочитает
его через MCP и соберёт вёрстку. Это проверяет ровно ту цепочку, которой команда
будет пользоваться каждый день.

**Проверить на настоящем макете без токена тоже можно:** выгрузите его дома,
скопируйте каталог `.figma-vault/` на рабочую машину (или принесите через git) —
данные самодостаточны, в Figma сервер не ходит.
